# Fully AI-generated IDs and selfies

How TrueID handles an ID card or selfie made entirely by an image generator. There are two layers: one that can't be faked, and one that only proves something when it finds a mark.

## Layer 1: what a generator cannot produce (decides the case)

| Attack | Why it fails |
|---|---|
| A generated card with an invented identity | The QR either isn't there (*no readable QR*: no auto-approval), or is signed with the attacker's own key (*signature invalid*: rejected). A generator can't produce the issuer's signature. |
| A generated card with a real person's QR copied onto it | The signed QR wins: the printed details must agree with it, the form must agree with it, and the selfie must match the issuer's photo for that ID (registry, or UIDAI's photo inside a real Aadhaar QR). A generated face doesn't match. |
| A generated selfie | It must match the issuer's photo, pass the server-issued head-turn challenge across a burst of frames, and not be a picture seen before. |
| A generated identity used many times | The graph links shared faces, devices and typing rhythms, and the consortium network shares hashed identifiers across banks. |

This layer is tested in `backend/tests/test_provenance.py::test_a_fully_generated_card_cannot_carry_a_valid_issuer_signature` and the existing policy tests.

## Layer 2: provenance marks (strong when found, silent otherwise)

`backend/app/modules/document/provenance.py` reads every uploaded card and selfie for:

- **C2PA content credentials.** These are signed manifests that Google (Gemini, Imagen), OpenAI, Adobe Firefly and Microsoft attach to generated images. They are read and validated with `c2pa-python`. A manifest whose action declares `digitalSourceType` *trainedAlgorithmicMedia* (made by AI) or *compositeWithTrainedAlgorithmicMedia* (edited with AI) fails the required check *Photos are new and carry no AI-generator marker*, naming the generator. A camera's own C2PA signature (*digitalCapture*) is reported as positive provenance.
- **IPTC / XMP digital source type** and **generator names** in EXIF/XMP metadata. The list is kept specific, so genuine photos aren't flagged; for example, "Imagen" is the Spanish word for image.
- **Stable Diffusion web UI settings** in PNG text chunks.

Finding a mark is strong evidence. **Not finding one proves nothing**: metadata is stripped by a screenshot or re-save. That's why Layer 1 does the deciding.

### SynthID

Google and its partners also embed a **SynthID** watermark in the pixels, which survives metadata stripping. Its detector isn't open source:

- Since October 2026 there is a public sign-in web portal (a few checks a day).
- There is also an enterprise detection API on Google Cloud.

Neither is a self-serve API this project can call, so SynthID isn't checked automatically. An analyst can upload a suspicious photo to the portal by hand. With enterprise access, the call belongs next to `read_c2pa()` in `provenance.py`, and its result would feed the same required check.

## What the analyst sees

- **Document tab:** *File provenance*, for example "C2PA content credentials say generated by AI (…)" or "no provenance metadata (this proves nothing either way)".
- **Face & liveness tab:** *Selfie file provenance*.
- **Reason codes:** `DOC_GENAI_METADATA` and `BIO_GENAI_METADATA`.

## A bug this work found

The pipeline's state didn't declare `selfie_raw`, and LangGraph drops undeclared keys. So the selfie's metadata check had **never run** on live or partner applications; only the card's had. This is fixed, with a regression test (`test_the_pipeline_keeps_the_raw_selfie_so_its_metadata_is_checked`).
